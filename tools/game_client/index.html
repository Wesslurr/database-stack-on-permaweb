Every interval, each simulated entity picks a new random target. Writes go through the same Write-Point path as player_red (Primary RAM → SD1/SD2 replication), signed with that entity's own owner. If an entity still has a write in flight, its newest target replaces the pending one ("coalesced") — so Achieved shows the real throughput the Primary sustains, not just what was requested.
Measured locally: L1 confirmed p50 ≈ 580 ms (L0 accept p50 ≈ 198 ms). With 2 writes in flight the cluster confirms roughly 3–4 writes/s in total; more in flight only increases latency. With 35 entities, each entity can really update about every ~10 s. Shorter intervals still work, but extra targets get coalesced. player_red shares the same queue, so WASD gets slower while the swarm runs.
